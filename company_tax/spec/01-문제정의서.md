## 1. 개요

### 1.1 목적

세무사·보험 FC가 상속·증여·법인승계 상담을 수행할 때, **상담 전 사전검토 단계**에서 고객 정보를 수집·정리하고 세액을 개산하여 검토보고서 초안을 산출하는 시스템을 정의한다. 본 문서는 그 필요성의 근거(AS-IS의 문제)와 달성 목표(TO-BE)를 규정하며, 후속 문서인 [요구사항 명세서](02-요구사항명세서.md)의 입력이 된다.

### 1.2 대상 업무 / 범위

**대상 업무**: 세무사·보험 FC(재무설계사)가 **상속·증여·법인승계 상담 전에 수행하는 사전검토** — 고객 사전정보 수집, 상담 유형 분류, 누락 정보 확인, 세액 개산, 쟁점 정리, 검토보고서 초안 작성.

**시스템 구성 (v2.0 플로우)**

| 계층 | 구성 |
|---|---|
| 입력 | 고객 사전정보 (대화형 입력) |
| 데이터·색인 | 세법·국세청 자료 + 기준일자 메타데이터 / 유형별 필수정보 체크리스트 / KURE-v1(fp16) → FAISS |
| 추론 | **GPT API (gpt-4o-mini)** — 유형분류 · 누락 질문 · 쟁점 정리 / **세액 계산은 Python 함수로 분리** |
| 출력·UI | 사전검토보고서 초안 / Vue.js + FastAPI |
| 반입 패키지 | 세법 자료 + FAISS 인덱스 / KURE-v1(fp16) / 세액 계산 모듈 + Vue 빌드 |

> **핵심 설계 원칙**: 예상 세액을 LLM이 계산하지 않도록 분리한다. 이는 **산술 오류**와 **근거 추적 불가** 문제를 동시에 해결하며, 세액 계산이 코드이므로 반입 후 LLM을 교체해도 그대로 동작한다.

**대상 세목 (8종)** — 우선순위 조사([asset-holder-tax-concerns.md](../docs/asset-holder-tax-concerns.md))에 근거한 개발 순서:

| 순서 | 세목 | 영역 | 상태 |
|---|---|---|---|
| 1 | 상속세 | 개인 | **완료** |
| 2 | 증여세 | 개인 | 차기 |
| 3 | 종합부동산세 | 개인 | 계획 |
| 4 | 양도소득세 | 개인 | 계획 |
| 5 | 가업승계(가업상속공제) | 법인 | 계획 |

| 8 | 주식이동 증여세 | 법인 | 계획 |

**범위 밖**: 실제 세무 신고서 제출, 홈택스 연동 전자신고, 세무 대리 행위, 개별 고객의 확정 세액 산출(본 도구의 결과는 개산이며 법적 효력이 없음).

## 2. AS-IS (현행)

### 2.1 현행 프로세스

| 단계 | 담당 | 수행 내용 |
|---|---|---|
| ① 고객 자산 청취 | 세무사·FC | 상담 중 구두로 부동산·금융자산·기타자산 규모를 청취, 메모 |
| ② 세법 확인 | 세무사·FC | 국세청·국가법률정보센터에서 해당 세목의 세율표·공제 요건을 개별 조회 |
| ③ 세액 산출 | 세무사·FC | 엑셀 수식 또는 수기 계산으로 과세표준·산출세액 계산 |
| ④ 공제 적용 판단 | 세무사 | 일괄공제 vs 기초+인적공제 유불리, 배우자공제 한도 등을 개별 판단 |
| ⑤ 결과 전달 | 세무사·FC | 계산 결과를 구두 또는 별도 문서로 고객에게 설명 |
| ⑥ 시나리오 재계산 | 세무사·FC | 고객이 조건을 바꿔 물으면 ③~⑤ 반복 |

### 2.2 Pain Point

| # | Pain Point | 근거 |
|---|---|---|
| P1 | **상담 중 즉시 답변 불가** — 세액 산출에 시간이 걸려 "확인 후 연락드리겠다"로 종료되는 경우가 잦음 | `[가정]` 현장 관행 |
| P2 | **공식 모의계산 도구의 공백** — 홈택스는 양도세·증여세·연말정산 모의계산을 제공하지만 **법인세 모의계산은 제공하지 않음**. 상속세도 로그인 기반이라 상담 현장에서 즉시 쓰기 어려움 | [tax-law-sources.md](../docs/tax-law-sources.md) 조사 결과 |
| P3 | **공제 유불리 판단의 수작업 의존** — 일괄공제/기초+인적공제 선택, 배우자공제 3중 한도(실제 상속액·법정상속분·30억) 등은 계산기 없이는 오판 위험 | 상속세및증여세법 구조 |
| P4 | **세법 개정 추적 부담** — 2026년 세제개편안으로 법인세율 전 구간 1%p 인상, 가업상속공제 전면 개편(경영기간 10→30년, 공제한도 "경영연수×20억원, 최대 1,000억원") 등이 예정되어 기존 계산 근거가 무효화됨 | [2026-tax-reform-summary.md](../docs/2026-tax-reform-summary.md) |
| P5 | **재계산 비용** — 조건 변경 시 처음부터 다시 계산해야 하므로 시나리오 비교 상담이 사실상 어려움 | `[가정]` P1에서 파생 |
| P6 | **가업승계 제도의 저활용** — 가업상속공제 이용 건수가 한국 110건 vs 독일 28,482건 수준으로, 제도가 있어도 계산·요건 판단이 어려워 활용되지 못함 | [asset-holder-tax-concerns.md](../docs/asset-holder-tax-concerns.md) |

## 3. 문제 정의

### 3.1 핵심 문제

> **세무 상담 현장에서 "지금 이 자리에서" 신뢰할 수 있는 세액을 산출할 수단이 없다.**

### 3.2 근본 원인

| # | 근본 원인 | 연관 Pain Point |
|---|---|---|
| R1 | 공식 모의계산 서비스가 세목별로 불완전하고(법인세 부재), 로그인·공인인증 등 진입 장벽이 있어 상담 중 사용이 불가능 | P2 |
| R2 | 세액 계산이 다단계 조건 분기(공제 선택, 3중 한도, 누진구간)를 포함해 암산·수기 계산으로는 오류 발생이 불가피 | P3, P6 |
| R3 | 세법이 매년 개정되어, 계산 로직을 코드로 관리하지 않으면 개정 반영 여부를 추적할 수 없음 | P4 |
| R4 | 개인 자산가용 도구와 전문가용 도구가 분리되어 있어, 같은 상담 자리에서 두 관점(개괄/정밀)을 오갈 수 없음 | P1, P5 |

### 3.3 영향

- **상담 전환율 저하**: 즉답 불가로 상담이 중단되면 후속 접촉률이 떨어짐 `[가정]`
- **오산 리스크**: 수기 계산 오류가 고객에게 전달될 경우 신뢰 손상 및 분쟁 소지
- **제도 사각지대**: 가업상속공제처럼 계산이 복잡한 제도는 아예 검토 대상에서 제외됨 (P6)

## 4. TO-BE

### 4.1 AS-IS / TO-BE 대비

| 구분 | AS-IS | TO-BE |
|---|---|---|
| 세액 산출 시점 | 상담 후 별도 작업 | **상담 중 즉시** |
| 산출 수단 | 엑셀·수기 + 세법 개별 조회 | 브라우저에서 바로 여는 단일 계산기 |
| 공제 유불리 판단 | 담당자 개별 판단 | **자동 비교 후 유리한 쪽 적용** |
| 시나리오 비교 | 사실상 불가 | 입력값 수정 후 재계산 (즉시) |
| 세법 개정 반영 | 담당자 개인 학습에 의존 | 계산 로직을 코드로 관리, 개정 시 테스트로 회귀 검증 |
| 사용자 층 | 전문가 전용 | **간단 모드(자산가 본인) + 상세 모드(전문가)** 이중 구조 |
| 결과 신뢰성 표시 | 구두 설명에 의존 | 화면에 개산 안내문구 상시 노출 |
| 정보 수집 | 구두 청취 후 메모, 누락은 상담 후 발견 | **대화형 입력 + 유형별 필수정보 체크리스트로 누락 항목 자동 질문** |
| 상담 유형 판단 | 담당자 경험에 의존 | 상속/증여/법인승계 **유형 자동 분류** |
| 세법 근거 확보 | 담당자가 개별 검색 | **RAG 검색(KURE-v1 + FAISS)으로 기준일자 포함 근거 자동 제시** |
| 쟁점 도출 | 담당자 경험에 의존 | LLM이 쟁점 정리 초안 제시 (전문가 검토 전제) |
| 산출물 | 없음 (구두 전달) | **사전검토보고서 초안** (기준일자·적용 전제·전문가 검토 문구 포함) |

### 4.2 개선 아이디어

1. **계산 로직과 화면의 분리** — 계산 로직을 UI 비의존 모듈로 두어 자동 테스트로 정확성을 상시 검증 (→ [프로젝트 원칙](03-프로젝트원칙.md) 제1·2조)
2. **이중 모드 UI** — 최소 입력만으로 개산을 얻는 간단 모드와, 개별 공제 항목을 통제하는 상세 모드를 하나의 화면에서 전환
3. **현장 친화 단위 체계** — 원 단위 대신 만원 단위 입력, 결과는 "N억 N,NNN만원" 표기로 상담 중 구두 전달이 쉽도록 함
4. **세목별 독립 배포** — 8개 계산기를 각각 독립 실행 가능한 형태로 만들고, 완성 후 통합 여부를 별도 판단 (조기 일반화 회피)
5. **개산 고지의 구조화** — 결과 화면에 참고용 개산임을 상시 표시하여 오해·분쟁 소지를 차단

| 세무사·FC (주 사용자) | 상담 현장에서의 정확성·속도. 오산 시 본인 신뢰도 직결 | 높음 |
| 자산가 고객 | 본인 세부담 규모 파악. 결과의 신뢰성 | 높음 |
| 프로젝트 개발자 (brugl) | 구현·유지보수. 세법 개정 반영 책임 | 높음 |
| 세법 개정 주체 (재정경제부·국세청) | 계산 근거의 원천. 개정 시 본 도구 갱신 필요 | 중간 (일방향) |
| 감독·규제 기관 | 개인정보 처리, 세무 대리 행위 저촉 여부 | 중간 |

| **C1'** | 기술 스택은 **사내 승인 스택으로 한정** — Vue.js, FastAPI, Python, FAISS, KURE-v1(fp16), gpt-4o-mini | 사내 반입 가능 기술 검토 결과. 승인 외 스택 추가 시 사전 협의 필수 (Agent Don't Rule ①) |

| **C7** | **세액 계산에 LLM을 사용하지 않는다.** 세액은 Python 코드로만 산출한다 | 산술 오류 방지 + 근거 추적성 확보. LLM 교체 시에도 계산 결과 불변 |
| **C8** | LLM 호출은 **단계별로 분리**하고 각 단계 출력에 스키마 검증을 적용한다 | 3단계(유형분류·누락질문·쟁점정리)를 한 번에 호출하면 오류 격리와 재시도가 불가능 |
| **C9** | 반입 패키지는 **오프라인 반입 가능**해야 한다 (세법 자료 + FAISS 인덱스 + KURE-v1 fp16 + 세액 계산 모듈 + Vue 빌드) | 사내 반입 절차상 외부 다운로드 없이 동작해야 함 |

## 9. 성공 기준 (KPI)

| KPI | 현재값 (AS-IS) | 목표값 (TO-BE) | 측정 시점 |
|---|---|---|---|
| K1. 세목 커버리지 | 0/8 | 8/8 완성 | 로드맵 종료 시 (세목별 완료 시마다 갱신) |
| K2. 계산 정확성 — 자동 테스트 통과율 | 해당 없음 (수기) | **100%** (세목별 전 시나리오) | 세목별 구현 완료 시 |
| K3. 세목당 검증 시나리오 수 | 해당 없음 | **세목당 5개 이상** (경계·예외 포함) | 세목별 구현 완료 시 |
| K4. 세액 산출 소요 시간 | `[가정]` 5~15분 (수기) | **60초 이내** (입력~결과 표시) | 세목별 구현 완료 시 |
| K5. 법정 산식 대비 결과 일치 | `[가정]` 편차 존재 | **오차 0원** (원 단위) | 세목별 구현 완료 시 |
| K6. 개산 고지 노출 | 없음 | 결과 표시 화면 **100%** 노출 | 세목별 구현 완료 시 |
| K7. 보안 원칙 위반 건수 | 해당 없음 | **0건** (개인정보 저장·전송, 하드코딩 인증정보) | 세목별 구현 완료 시 |
| **K8. 외부 LLM 전송 시 개인식별정보 노출** | 해당 없음 | **0건** (마스킹 미적용 전송 0건) | 사전검토 시스템 공개 전 · 이후 상시 |
| **K9. LLM 산술 계산 발생 건수** | 해당 없음 | **0건** (세액은 전량 코드 산출) | 사전검토 시스템 공개 전 |
