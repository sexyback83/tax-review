## 1. 개요

### 1.1 대상 기능

[요구사항 명세서](02-요구사항명세서.md)의 FR-01~FR-23 및 NFR-01~NFR-13 전체를 대상으로 하되, 구현 상세는 세목별 진행 상태에 따라 다음과 같이 구분한다.

| 구분 | 대상 | 본 문서에서의 기술 수준 |
|---|---|---|
| 완료 | 상속세 (FR-08~14) | 확정된 구현 구조를 기술 |
| 차기 | 증여세 (FR-15) | 적용할 아키텍처 패턴을 기술 |
| 계획 | 나머지 6개 세목 (FR-16~21) | 공통 원칙과 확장 방식만 기술 |
| 향후 | 통합 셸·AI 어드바이저 (FR-22~23) | 착수 조건(게이트)만 기술 |

### 1.2 목표

1. 계산 로직을 UI로부터 완전히 분리하여, 브라우저 없이 자동 검증 가능한 구조를 확립한다 ([원칙](03-프로젝트원칙.md) 제1·2조).
2. 세목 추가 시 기존 세목의 코드 변경이 발생하지 않는 구조를 유지한다 (NFR-11).
3. 서버·저장소·네트워크를 구조적으로 배제하여 정보 유출 경로 자체를 제거한다 ([원칙](03-프로젝트원칙.md) 제4조).

### 1.3 범위 / 비범위

**범위**: 세목별 계산 모듈 설계, 화면 계층 설계, 테스트 전략, 세목 간 확장 방식.

**비범위**: 서버·데이터베이스 설계(존재하지 않음), 인증·인가 설계(원칙 제5조 활성화 조건 미충족), 배포 파이프라인(정적 파일 직접 실행), AI 컴포넌트 설계(FR-23 착수 전).

## 2. 요구사항 분석 요약

| 요구사항 ID | 요약 | 기술적 함의 |
|---|---|---|
| FR-01 | 세목별 독립 계산기 | 세목당 폴더 1개, 파일 3개. 세목 간 `import`/참조 금지. 공통 코드 추출은 실제 중복 발생 후로 유예 (원칙 제8조) |
| FR-02 | 간단/상세 모드 | 상세 필드를 계산 함수의 **선택 파라미터**로 설계하고 기본값을 부여. 간단 모드는 해당 인자를 전달하지 않는 것만으로 동작 |
| FR-03·04 | 만원 입력 / 억·만원 출력 | 단위 환산은 **화면 계층 전용 책임**. 계산 모듈은 원 단위만 취급하여 로직과 표현을 분리 |
| FR-05 | 입력 검증 | 검증은 화면 계층에서 수행하고, 실패 시 계산 함수를 **호출하지 않는다**. 간단·상세 필드를 동일 기준으로 검증 |
| FR-06 | 개산 고지 | 결과 영역 내부에 배치하여 결과 표시 시에만 함께 노출 |
| FR-07 | 계산 단계 표시 | 계산 함수가 최종 세액뿐 아니라 **중간 산출값을 포함한 객체**를 반환하도록 설계 |
| FR-09~13 | 상속세 계산 규칙 | 각 공제를 **독립 순수 함수**로 분리. 오케스트레이션 함수가 이들을 조합. 함수 단위 테스트와 시나리오 테스트를 모두 가능하게 함 |
| FR-14 | 상세 모드 추가 입력 | 오케스트레이션 함수의 선택 파라미터로 흡수. 시그니처 변경 없이 확장 |
| FR-15~21 | 후속 세목 | 상속세와 동일한 3파일 패턴을 복제 적용. 세목별 계산 규칙만 상이 |
| NFR-01·02 | 성능·가용성 | 클라이언트 단독 연산 + 정적 파일. 서버 부재로 단일 장애점 자체를 제거 |
| NFR-03·04 | 정보 보호 | 저장소 API·네트워크 API를 **코드에 포함하지 않음**으로써 구조적으로 보장 |
| NFR-06 | 감사 추적 | Git 커밋을 추적 수단으로 사용. 계산 로직 변경 커밋에 테스트 결과 기재 |
| NFR-10 | 정확성 | 기대값을 법정 산식으로 직접 산출하여 테스트에 고정 (원칙 제3조) |
| NFR-12 | 유지보수성 | 세율·공제 한도를 **명명된 상수**로 분리하여 개정 시 변경 지점을 국소화 |
| NFR-13 | AI 안전성 | FR-23 착수 전까지 설계 대상 아님. 착수 시 원칙 제6조 10개 항목이 게이트 |

## 3. 기술 스택

**v2.0 스택 — 사내 승인 목록으로 한정** (제약 C1', 원칙 제7조)

| 영역 | 선택 기술 | 검토한 대안 | 선택 근거 |
|---|---|---|---|
| 프런트엔드 | **Vue.js** | React, Svelte, Vanilla JS | 사내 가용 스택. 대화형 다단계 입력(FR-24)과 누락 질문 흐름(FR-25)은 상태 관리가 필요해 v1.0의 Vanilla 방식으로는 관리 비용이 급증 |
| 백엔드 | **FastAPI** (Python) | Flask, Django, Node/Express | 사내 가용 스택. 세액 계산 모듈(Python)과 동일 런타임이라 계층 간 경계가 단순해짐. 스키마 검증(NFR-19)에 Pydantic을 그대로 활용 |
| 계산 로직 | **Python 함수 모듈** | LLM 계산, JS 유지 | **LLM 계산은 금지**(NFR-14) — 산술 오류·근거 추적 불가. Python 선택은 FastAPI와의 런타임 일치. *기존 JS 구현은 포팅 검증 기준으로 활용 — 미결 O7* |
| 임베딩 | **KURE-v1 (fp16)** | OpenAI Embeddings, 다국어 SBERT | 사내 가용 모델. fp16으로 반입 용량 절감. **외부 임베딩 API를 쓰면 세법 자료가 외부로 나가고 오프라인 반입(NFR-17)이 불가** |
| 벡터 DB | **FAISS** | Chroma, pgvector, Elasticsearch | 사내 가용. 파일 기반이라 인덱스를 그대로 반입 패키지에 포함 가능(NFR-17). 별도 서버 불필요 |
| LLM | **gpt-4o-mini** | Claude API *(1차안)*, 사내 모델 | 사내 가용 스택 반영으로 Claude → **gpt-4o-mini 확정**. 유형분류·누락질문·쟁점정리 3개 용도에 한정하며 세액 계산에는 사용 금지 |
| 데이터베이스 | *(미확정)* | — | 상담 건 저장·조회(NFR-05 RBAC)를 위해 필요. **선정 시 사내 승인 스택 확인 필요 — 미결 O12** |
| 테스트 도구 | **pytest** (Python) | unittest | 사내 표준 확인 필요. 계산 모듈은 서버 없이 단독 실행 가능해야 함(원칙 제2조) |
| 배포 | **오프라인 반입 패키지** | 클라우드 배포 | 사내 반입 절차. 세법 자료 + FAISS 인덱스 + KURE-v1(fp16) + 계산 모듈 + Vue 빌드를 한 묶음으로 구성(NFR-17, 제약 C9) |

> **v1.0 → v2.0 스택 전환 사유**: v1.0은 "프레임워크·서버·네트워크 없음"을 전제로 최소 스택을 선택했다. v2.0에서 RAG 검색·LLM 추론·대화형 입력·보고서 생성이 범위에 들어오면서 그 전제가 소멸했다. 다만 **세액 계산을 코드로 유지한다는 v1.0의 핵심 설계는 그대로 승계**되며, 오히려 v2.0에서 "LLM에게 계산을 맡기지 않는다"는 명시적 금지 조항(NFR-14)으로 강화되었다.

### 4.2 데이터 모델

계산 계층은 **영속 엔티티를 갖지 않으며**, 함수 호출 시점의 입출력 구조만 존재한다.

**입력 구조 (`calculateInheritanceTax` 인자)** — 모든 금액은 **원 단위**

| 속성 | 타입 | 필수 | 기본값 | 관련 요구사항 |
|---|---|---|---|---|
| `realEstate` | number | ✔ | — | FR-08 |
| `cash` | number | ✔ | — | FR-08, FR-12 |
| `other` | number | | `0` | FR-08 |
| `hasSpouse` | boolean | ✔ | — | FR-11 |
| `numChildren` | number | ✔ | — | FR-10, FR-11 |
| `debt` | number | | `0` | FR-14 |
| `funeralCost` | number | | `0` | FR-14 |
| `priorGift` | number | | `0` | FR-14 |
| `financialDebt` | number | | `0` | FR-12, FR-14 |
| `actualSpouseShare` | number \| null | | `null` | FR-11, FR-14 |
| `minorYearsTotal` | number | | `0` | FR-10, FR-14 |
| `numElderly` | number | | `0` | FR-10, FR-14 |
| `disabledYearsTotal` | number | | `0` | FR-10, FR-14 |

> **설계 의도**: 필수 5개는 간단 모드(FR-02·NFR-09), 선택 8개는 상세 모드에 대응한다. 선택 파라미터에 기본값을 두어 **하나의 함수가 두 모드를 모두 처리**하며, 모드 분기 로직이 계산 계층에 침투하지 않는다.

**출력 구조 (반환 객체)**

| 속성 | 타입 | 설명 | 관련 요구사항 |
|---|---|---|---|
| `totalEstate` | number | 총 상속재산가액 (3분류 합계) | FR-07, FR-08 |
| `taxableValue` | number | 과세가액 (− 채무·장례비 + 사전증여) | FR-07 |
| `taxBase` | number | 과세표준 (0 미만은 0으로 절하) | FR-07 |
| `calculatedTax` | number | 산출세액 | FR-07, FR-09 |
| `reportDeduction` | number | 신고세액공제 (3%) | FR-07, FR-13 |
| `finalTax` | number | 최종 납부세액 | FR-07 |
| `breakdown.standardDeduction` | number | 적용된 기본 공제액 | FR-10 |
| `breakdown.spouseDeduction` | number | 배우자상속공제액 | FR-11 |
| `breakdown.financialDeduction` | number | 금융재산상속공제액 | FR-12 |
| `breakdown.totalDeduction` | number | 공제 합계 | FR-10~12 |

> **반올림 규칙**: 개별 공제 함수는 **반올림하지 않은 값**을 반환하고, 오케스트레이션 함수에서 `taxBase`·`calculatedTax`·`reportDeduction`에 `Math.round`를 **1회만** 적용한다. 중간 단계마다 반올림하면 오차가 누적되므로 이를 금지한다.
>
> `breakdown` 내부 값은 반올림되지 않은 원시값이므로 **화면에 직접 표시하지 않는다.** 표시가 필요해지면 화면 계층에서 포맷한다.

### 4.3 모듈 계약

> HTTP API가 존재하지 않으므로, 원 템플릿의 "API 계약"을 **모듈 함수 계약**으로 해석하여 기술한다. 이 시그니처는 세목 간·문서 간 공유되는 확정 계약이며, 변경 시 [원칙 §6 개정 절차](03-프로젝트원칙.md#6-개정-절차)를 따른다.

| 함수 | 입력 | 출력 | 계약 내용 | 관련 요구사항 |
|---|---|---|---|---|
| `calculateProgressiveTax` | `(taxBase: number)` | `number` | 과세표준이 0 이하면 0을 반환. 그 외에는 해당 구간의 `세율 × 과세표준 − 누진공제액` | FR-09 |
| `calculateStandardDeduction` | `({numChildren, minorYearsTotal?, numElderly?, disabledYearsTotal?, isSpouseSoleHeir?})` | `number` | 일괄공제(5억)와 [기초 2억 + 인적공제] 중 **큰 값**. `isSpouseSoleHeir`가 참이면 일괄공제를 배제하고 인적공제 합계만 반환 | FR-10 |
| `calculateSpouseDeduction` | `({hasSpouse, netEstate, numChildren, actualSpouseShare?})` | `number` | 배우자 없으면 0. 그 외 `min(실제상속액, 법정상속분, 30억)`을 구한 뒤 5억 미만이면 5억으로 절상. `actualSpouseShare`가 `null`이면 법정상속분을 실제상속액으로 간주 | FR-11 |
| `calculateFinancialAssetDeduction` | `({cash, financialDebt?})` | `number` | 순금융재산 = `max(0, cash − financialDebt)`. 그 20%가 2천만원 미만이면 `min(순금융재산, 2천만)`, 아니면 `min(20%, 2억)` | FR-12 |
| `calculateInheritanceTax` | `(입력 구조 §4.2)` | `출력 구조 §4.2` | 위 4개 함수를 조합. 반올림은 이 함수에서만 수행 | FR-07, FR-08, FR-13, FR-14 |

**공통 계약 조건**

- 모든 함수는 **순수 함수**다. 외부 상태를 읽거나 쓰지 않으며, 동일 입력에 항상 동일 출력을 반환한다.
- 모든 함수는 `module.exports`로 노출되며 동시에 전역에 선언되어 브라우저에서도 접근 가능하다.
- 입력값 검증(음수·비수치)은 **화면 계층의 책임**이며, 계산 함수는 유효한 입력을 전제한다.
  단, 순손익액은 결손(음수)이 유효한 입력이다. 0원 하한은 법정 규칙이므로 화면이 아니라
  `calculateUnlistedStockValue` 안에서 건다 (상증령 제56조 제1항).

### 4.4 세목 확장 방식 (FR-15~21)

새 세목 추가 시 다음 절차를 따른다. **기존 세목의 파일은 변경하지 않는다** (NFR-11).

1. `company_tax/<세목-영문명>/` 폴더 생성
2. 해당 세목의 세율·공제 상수를 `calc.js` 상단에 명명된 상수로 정의 (근거 법령 주석 필수)
3. 공제·세액 계산을 각각 독립 순수 함수로 작성 (테스트 우선 — 원칙 제3조)
4. 오케스트레이션 함수가 이들을 조합하고, 반올림을 1회 수행
5. `index.html`은 상속세 화면을 **복제 후 수정**한다 — 공통 UI 모듈로 추출하지 않는다 (원칙 제8조: 실제 중복이 3회 이상 반복될 때까지 추출 유예)

## 9. Quickstart 검증 시나리오

새 개발자·검토자가 본 프로젝트의 정상 동작을 확인하는 최단 경로.

### 9.1 자동 검증

```bash
node company_tax/inheritance-tax/calc.test.js
```

**기대 결과**: 26개 항목이 모두 `PASS`로 출력되고 종료 코드가 `0`.

### 9.2 화면 검증 — 간단 모드

1. `company_tax/inheritance-tax/index.html`을 브라우저로 연다.
2. 입력: 부동산가액 `180000`, 현금(금융자산)가액 `20000`, 기타자산가액 `0`, **배우자 있음 체크**, 자녀 수 `2`
3. `계산하기` 클릭

**기대 결과**

| 항목 | 값 |
|---|---|
| 총 상속재산가액 | 20억원 |
| 과세표준 | 6억 286만원 |
| 산출세액 | 1억 2,086만원 |
| 신고세액공제(3%) | 363만원 |
| **최종 납부세액** | **1억 1,723만원** |

개산 안내문구가 결과 하단에 함께 표시되어야 한다 (FR-06).

### 9.3 화면 검증 — 상세 모드

1. `상세 모드 (세무사/FC용)` 체크 → 추가 입력 필드 8개가 나타난다.
2. 입력: 부동산가액 `150000`, 현금 `0`, **배우자 있음 체크**, 자녀 수 `2`, 미성년자 잔여연수 합계 `25`
3. `계산하기` 클릭

**기대 결과**: 최종 납부세액 **4,989만원** (내부 계산값 49,885,714원 → 만원 단위 반올림 표기)

### 9.4 검증 실패 확인 (FR-05)

상세 모드에서 `채무` 필드에 `-10000`을 입력하고 계산하면, 오류 메시지가 표시되고 **결과가 표시되지 않아야 한다.**

> **주의**: 일부 브라우저는 `file://` 프로토콜에서 외부 스크립트 로드를 제한할 수 있다. 이 경우 해당 폴더를 정적 서버로 서빙한 뒤 `http://` 로 접근하여 검증한다.
